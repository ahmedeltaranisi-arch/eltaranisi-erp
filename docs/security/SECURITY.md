# الأمان والصلاحيات — ELTARANISI ERP

## 1. نموذج التهديد (مختصر)

| التهديد | الضابط الحالي |
|---|---|
| سرقة بيانات دخول | PBKDF2-SHA256 بـ 240,000 تكرار + ملح عشوائي لكل مستخدم؛ لا كلمات مرور في الكود |
| تخمين كلمة المرور | حد 8 محاولات ثم قفل 15 دقيقة + رسالة خطأ موحدة |
| سرقة الجلسة | الرمز يُولَّد عشوائيًا (`secrets.token_urlsafe(32)`) ويُخزَّن **مُهاشًا** فقط (SHA-256) |
| تصعيد صلاحيات | كل مسار API يعلن صلاحية تُفحص على الخادم قبل التنفيذ؛ منع منح دور `super_admin` |
| IDOR (الوصول لكيان شركة أخرى) | كل استعلام مقيّد بـ `company_id` من الجلسة، لا من الطلب؛ اختبار عزل مُنفّذ |
| احتيال داخلي | فصل مهام، سجل تدقيق لا يُعدّل، عتبات اعتماد |
| تعديل/حذف قيد مرحّل | ممنوع في المحرك؛ التصحيح بقيد عكسي موثّق |
| CSRF | الواجهة تستخدم `Authorization: Bearer` (لا كوكيز) ⇒ لا CSRF تقليديًا |
| XSS | كل النصوص المدرجة في الواجهة تمرّ عبر `ESC()`؛ لا `innerHTML` لبيانات مستخدم غير مهروبة |
| SQL Injection | استعلامات مُعاملة (`?`) في كل مكان؛ لا دمج نصوص في SQL |
| حقن JSON/مدخلات | تحقق نوعي على الخادم + رفض الحقول غير المتوقعة |
| كشف أسرار | لا مفاتيح في المستودع؛ إعدادات البيئة خارجها (`docs/deployment`) |

## 2. المصادقة والجلسات

- كلمة المرور: 10 أحرف على الأقل عند الإنشاء/التغيير، مُهاشّة، ولا تُسجَّل في أي سجل.
- الجلسة: 12 ساعة، تُلغى بـ `revoked=1` عند تسجيل الخروج، وتُحفظ فقط بصمة الهاش + IP + User-Agent.
- إعادة تعيين كلمة المرور: عبر مدير النظام (يجب تغييرها عند أول دخول: `password_must_change`).
- **MFA غير منفذة** — مطلوبة قبل الإنتاج (TOTP + أجهزة موثوقة + سجل جلسات قابل للإلغاء).

## 3. التفويض (RBAC)

- 10 أدوار جاهزة، لكل دور قائمة صلاحيات `module.action`.
- `*` = كل الصلاحيات (مالك الشركة فقط)، و`module.*` مدعومة.
- نطاقات البيانات: `platform` (مدير المنصة)، `company`، `read_only` (مراجع).
- **مدير المنصة لا يملك وصولًا تلقائيًا للبيانات المالية** (`platform.manage` فقط).
- فحص الصلاحية يحدث دائمًا في `server.py` قبل تنفيذ الدالة — إخفاء عنصر في الواجهة ليس ضابطًا.
- تغيير الأدوار متاح من `/api/users` ويُسجل في سجل التدقيق.

## 4. سجل التدقيق

يُسجَّل تلقائيًا: الدخول، إنشاء/ترحيل/عكس القيود، ترحيل الفواتير والسندات، إنشاء الحسابات/العملاء/
الموردين/المستخدمين، تعديل الأدوار، إقفال/إعادة فتح الفترات، تصدير التقارير، وأي تغيير إعدادات.

السجل يحتوي: `user_id`, `username`, `action`, `entity`, `entity_id`, `details(JSON)`, `ip`, `created_at`.
**لا يوجد في الـ API أي مسار لتعديل أو حذف سجل التدقيق.**

## 5. حماية الملفات والمرفقات

- مخطط التخزين خارج المسار العام: `data/uploads/` والمجلد `static/` لا يقدّم إلا ملفات الواجهة.
- التحقق المطلوب عند تفعيل الرفع: النوع (allow-list)، الحجم، فحص محتوى، وتخزين باسم عشوائي.
- ⚠️ رفع المرفقات **غير منفذ** في هذه النسخة (الجدول موجود).

## 6. رؤوس HTTP والحدود

- `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: same-origin`.
- حد حجم الطلب 8MB، حد حجم صفحات القوائم (per_page ≤ 200).
- **Rate limiting** غير منفذ على مستوى التطبيق — يُنصح به في بوابة الإنتاج (Nginx/Cloudflare).
- HTTPS/TLS: يجب إنهاؤه في بوابة أمام الخادم (الخادم الحالي HTTP داخل الشبكة فقط).

## 7. النسخ الاحتياطي

- سكربت `infra/backup.sh` ينسخ قاعدة SQLite بأمان (`VACUUM INTO`) + ضغط + تشفير اختياري بـ `age`/`gpg`.
- اختبار استعادة: `infra/restore.sh <archive>`.
- RPO/RTO مقترح لبيئة بها هذا الحجم: RPO ≤ 15 دقيقة (نسخ كل 15 دقيقة)، RTO ≤ 30 دقيقة.
- ⚠️ لم يُنفَّذ اختبار استعادة آلي في CI لهذه النسخة.

## 8. حدود معروفة يجب معالجتها قبل الإنتاج

1. MFA وإدارة الأجهزة، وقائمة إلغاء الجلسات لكل مستخدم.
2. Rate limiting وWAF وحماية DDoS.
3. HTTPS إلزامي + HSTS + سياسة CSP صارمة.
4. إدارة أسرار عبر Vault/Secrets Manager وليس ملفات.
5. مراجعة أمنية خارجية واختبار اختراق.
6. RLS في PostgreSQL كطبقة عزل ثانية.
7. تصفية/تشفير الحقول الحساسة (الرواتب، بيانات البنوك) حسب نموذج التهديد.
