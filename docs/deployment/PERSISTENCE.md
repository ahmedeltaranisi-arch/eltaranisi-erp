# حفظ البيانات بشكل دائم / Persistent storage

> **الخلاصة:** التطبيق يحفظ كل شيء في قاعدة بيانات SQLite على القرص (`ERP_DB`).
> على أي سيرفر له قرص دائم (VPS / Docker / أي استضافة عادية) البيانات تبقى للأبد،
> وتم اختبارها: تُسجّل قيدًا، تخرج من النظام، تعيد تشغيل السيرفر، وتدخل مرة أخرى —
> البيانات موجودة كما هي.
>
> المشكلة الوحيدة في نشر **Vercel** تحديداً: الملف الوحيد القابل للكتابة هناك هو
> `/tmp`، وهو **مؤقت** ويُمسح مع كل إعادة نشر أو إعادة تشغيل للنسخة (cold start).
> لذلك أي بيانات تُدخل على ذلك الرابط تُفقد عند أول إعادة تشغيل.

---

## 1) لماذا تُفقد البيانات على Vercel؟

| السبب | التفصيل |
|---|---|
| نظام ملفات للقراءة فقط | Vercel يسمح بالكتابة في `/tmp` فقط |
| نسخ متعددة (serverless) | كل نسخة لها `/tmp` خاص بها، ولا تشارك غيرها |
| نسخ تُعاد دوريًا | نسخة الخمول تُقتل ثم تُعاد من الصفر → `seed.py` ينشئ قاعدة جديدة |

نجد ذلك برمجياً في `api/index.py`:

```python
os.environ.setdefault("ERP_DB", "/tmp/eltaranisi-erp/erp.db")
```

## 2) الحلول الممكنة (اختر واحداً)

### أ) قاعدة بيانات Postgres مُدارة + Vercel (موصى به إن أردت البقاء على Vercel)
1. أنشئ قاعدة مجانية على [Neon](https://neon.tech) أو [Supabase](https://supabase.com).
2. انسخ `DATABASE_URL` (يبدأ بـ `postgresql://`).
3. أرسل الرابط — يتم تحويل طبقة التخزين إلى Postgres، ويصبح كل ما يُدخل محفوظًا
   بشكل دائم ومشترك بين كل النسخ.
   *ملاحظة:* التحويل يشمل بناء المخطط مرة واحدة وترحيل البيانات الحالية.

### ب) سيرفر له قرص دائم (أسرع وأرخص على المدى الطويل، وبدون تغيير كود)
التطبيق جاهز: `Dockerfile` + `docker-compose.yml` + `nginx.conf` في `infra/`،
وقاعدة البيانات تُحفظ في volume:

```yaml
services:
  erp:
    build: .
    environment:
      ERP_DB: /data/erp.db          # داخل القرص الدائم
      ERP_SECRET_KEY: <random-48>
    volumes:
      - erp-data:/data
volumes:
  erp-data:
```

يعمل على أي VPS (2 GB RAM تكفي)، أو على Fly.io / Railway / Render مع Volume.
نحتاج فقط بيانات الاتصال بالسيرفر (SSH) أو حساب المنصة لنشره.

### ج) نسخ احتياطية دورية (حل مؤقت على Vercel الحالي)
- زر **«نسخة احتياطية»** في الشريط الأحمر أعلى الشاشة ينزّل ملف `.db` كامل
  (`GET /api/admin/backup`، مقيّد بصلاحية إعدادات الشركة ومسجّل في سجل التدقيق).
- استرجاع الملف في أي مكان:

```bash
ERP_DB=/path/erp.db python3 scripts/restore_backup.py eltaranisi-erp-backup-20261021-104500.db
```

  السكربت يتحقق أولًا (جداول موجودة + ميزان مراجعة متوازن)، ويحتفظ بنسخة من
  القاعدة الحالية قبل الاستبدال.

## 3) كيف تعرف أن النشر دائم؟

```bash
curl https://<your-host>/api/health
# {"status":"ok", ..., "storage": {"durable": true}}   ← دائم
# {"status":"ok", ..., "storage": {"durable": false}}  ← مؤقت (تنبيه أحمر في الواجهة)
```

وللتفاصيل (المسار، الحجم، عدد الصفوف، النسخ الاحتياطية):

```bash
curl -H "Authorization: Bearer <token>" https://<your-host>/api/admin/storage
```

## 4) ما تم اختباره فعليًا

| السيناريو | النتيجة |
|---|---|
| إضافة بند مديونية ثم **تسجيل خروج** ثم **تسجيل دخول** | البند والمستحق كما هما (اختبار `B139` اليدوي + `B122`) |
| **إعادة تشغيل السيرفر** بعد الخروج | البيانات موجودة — الملف على القرص وليس في الذاكرة |
| تنزيل نسخة احتياطية | ملف `SQLite format 3` كامل، 47 جدولًا، ميزان متوازن (`B138`) |
| استرجاع النسخة | `scripts/restore_backup.py` يتحقق ثم يستبدل مع الاحتفاظ بنسخة أمان |
| نشر Vercel الحالي | `storage.durable = false` → تنبيه ظاهر للمستخدم |

## 5) ملاحظات تشغيلية

- لا تضع `ERP_DB` داخل مجلد يخدمه الويب (خصوصًا `static/`).
- `ERP_SECRET_KEY` ثابت ومشترك ضروري إذا كانت هناك أكثر من نسخة تعمل بالتوازي.
- نسخ احتياطي يومي على السيرفر: `infra/backup.sh` (يدعم التشفير بـ age/GPG).
- الاحتفاظ بالنسخ: `RETENTION_DAYS` في `.env`.
