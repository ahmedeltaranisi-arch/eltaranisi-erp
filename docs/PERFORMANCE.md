# تقرير الأداء — لماذا الموقع ثقيل؟ (قياس فعلي على الإنتاج)

_قياسات مأخوذة من الموقع المنشور `eltaranisi-erp.vercel.app` في 2026-10-27، ومن عدّاد
استعلامات على نفس الكود محليًا._

## 1) الأرقام كما هي

| العملية | الزمن على الإنتاج | عدد جمل SQL لكل طلب |
|---|---|---|
| أول طلب بعد فترة خمول (cold start) | **26.0 ث** | — |
| فتح التطبيق (login + لوحة التحكم) | 6 طلبات متتالية | 7 + 11 + 33 + 5 … |
| `/api/meta` (قوائم الصفحات) | 1.6 – 2.3 ث | **11** |
| `/api/dashboard` (لوحة التحكم) | **5.7 – 6.3 ث** | **33** |
| `/api/vendors` (قائمة المقاولين) | 0.6 – 0.8 ث | 5 |
| `/api/debt/summary` | 0.6 – 0.8 ث | 5 |
| نموذج «سند دفع/تحصيل» (بياناته تُجلب معًا) | 1.3 – 1.4 ث (5 طلبات) | 5 طلبات × عدة استعلامات |
| حفظ سند دفع (`POST /api/payments`) | 0.9 ث | **36** |
| إضافة بند مديونية (`POST /api/debt/items`) | 0.8 ث | **31** |
| إضافة مورد/مقاول (`POST /api/vendors`) | 0.7 ث | 8 |

**السبب الجذري الأول:** قاعدة البيانات **Cloudflare D1** تُقرأ عبر HTTPS — يعني **كل جملة
SQL = رحلة شبكة كاملة (~120–170 مللي ثانية)**. أقصى عدد استعلامات في شاشة واحدة 33 =
5.7 ثانية فعلية، وحفظ سند = 36 استعلام + إعادة تحميل الصفحة = 45+ رحلة ≈ 6–7 ثوانٍ.
الموقع المحلي (SQLite على نفس الجهاز) يعطي نفس الشاشة في 8 مللي ثانية — لذلك لا يظهر البطء
في الاختبارات.

**السبب الثاني — الإقلاع البارد 26 ثانية:** `api/index.py` يشغّل `db.migrate()` مع كل
instance جديد، وهي **84 جملة SQL** (فحص أعمدة، إعادة إنشاء المخطط والفهارس) = ~9 ثوانٍ
إضافية على كل إقلاع، فوق تحميل موديولات التصدير (PDF/Excel) وأول اتصال بـ D1.

**السبب الثالث — مكان التشغيل:** الاستجابة تأتي من `x-vercel-id: pdx1` أي **أوريجون
(أمريكا الغربية)** والمستخدم في مصر: ~250 مللي ثانية رحلة ذهاب وعودة **لكل طلب**، مضروبة
في كل ما سبق.

**السبب الرابع — الواجهة:**
* فتح التطبيق يجري الطلبات **بالتسلسل** (`await` وراء `await`): meta ثم me ثم فحص التخزين
  ثم لوحة التحكم.
* كل حفظ يعمل `render()` كامل (طلب إضافي) بدل تحديث الصف في الذاكرة.
* `pages.js` حجمه **209 كيلوبايت** + `allowance.js` 39 كيلوبايت، وترويسة الملفات
  `cache-control: max-age=0, must-revalidate` → إعادة تحقّق في كل زيارة (الخطوط فقط هي
  المُخزَّنة `immutable`).

## 2) هل ليها حل؟ نعم — وبنفس الترتيب

| الإصلاح | الأثر المتوقع |
|---|---|
| **1. تخطّي `migrate()` في الإقلاع** (نسخة مخطط تُقرأ باستعلام واحد، والترحيل يبقى سكربتًا/عند الحاجة) | الإقلاع البارد 26 ث → **2–3 ث** |
| **2. تجميع الاستعلامات في رحلة واحدة** باستخدام `d1.batch()` الموجود أصلًا (لوحة التحكم 33 → 4، meta 11 → 2) | لوحة التحكم 5.7 ث → **0.5–0.7 ث** |
| **3. دمج نهاية النموذج**: `GET /api/payments/bootstrap` واحد يجمع (بنوك + عملاء + موردون + فواتير) | فتح النموذج 1.4 ث → **0.3 ث** |
| **4. كاش داخلي 60 ثانية للبيانات المرجعية** (meta/accounts/banks/customers/vendors) مع إبطال عند أي كتابة | فتح النموذج والشاشات المتكررة → **~0.05 ث** |
| **5. تشغيل الدالة في `fra1` (فرانكفورت)** بدل `pdx1` + `maxDuration` مناسب | توفير **~150–200 مللي ثانية** في *كل* طلب |
| **6. تحديث الواجهة تفاؤليًا**: بعد الحفظ تظهر الحركة فورًا ثم مزامنة في الخلفية بدل `render()` كامل | حفظ السند: إحساس فوري، **6–7 ث → 0.6 ث** للتأكيد |
| **7. الواجهة الخفيفة**: تشغيل طلبات الإقلاع بالتوازي (`Promise.all`)، إلغاء نداءَي `health`/`dev/accounts` غير الضروريين، تصغير `pages.js` وتقسيمه، وترويسة `immutable` للملفات | تحميل أول 250 ك.ب → **~70 ك.ب** وطلبات أقل |
| **8. (مُوصى به) قياس مستمر**: سكربت `scripts/perf_check.py` يطبع زمن كل نهاية وميضها | منع الرجوع للبطء |

## 3) ما لا يحتاج تغييرًا
* الاستعلامات نفسها سليمة والفهارس موجودة (`idx_lines_account`, `idx_debt_items_account`, …).
* التصدير PDF/Excel سريع نسبيًا لأن الخطوط تُحمَّل عند الطلب فقط.

## 4) ما تم تنفيذه (جولة الأداء — Round y)

| # | التغيير | الملف | القياس قبل → بعد |
|---|---|---|---|
| 1 | الإقلاع البارد لم يعد يشغّل `migrate()` كاملة: بصمة مخطط محفوظة في `app_meta.schema_version` واستعلام واحد يحدد الحاجة للترحيل | `db.ensure_schema()` + `api/index.py` | 84 جملة SQL لكل إقلاع → **1 استعلام** |
| 2 | استعلامات N+1 أُلغيت: `vendor_payables` (٢ لكل مورد) و`monthly_series` (١ لكل شهر) | `reports.py` | لوحة التحكم **33 → 16** استعلام |
| 3 | فتح نموذج سند الدفع/التحصيل: طلب واحد `/api/payments/bootstrap` بدل ٥ طلبات | `server.py` + `pages.js` | ٥ رحلات شبكة → **1** |
| 4 | كاش استجابة قصير (افتراضي 60 ثانية، `ERP_CACHE_TTL`) للبيانات المرجعية والشاشات للقراءة، **يُبطَل بأي كتابة** | `server.py` | الشاشة المتكررة → **~0 ث** |
| 5 | مذكّرة قراءة داخل الطلب: أي `SELECT` متكرر يُجاب من الذاكرة، وتُمسح عند أي كتابة | `db.MemoConnection` | استعلامات أقل في كل طلب |
| 6 | تشغيل الدالة في **fra1 (فرانكفورت)** بدل `pdx1` | `vercel.json` | **−150/200 مللي** في كل طلب |
| 7 | الإقلاع في الواجهة: `meta` + `me` بالتوازي، `health` مرة واحدة، فحص التخزين غير معطِّل | `app.js` | رحلة أقل + صفحة أسرع |
| 8 | ملفات `.js/.css` تُخزَّن ٥ دقائق (`stale-while-revalidate`) بدل `max-age=0` | `vercel.json` + `server.py` | تحميل أول أسرع بعد الزيارة الأولى |
| 9 | سكربت قياس `scripts/perf_check.py` | — | يقيس الإقلاع البارد وكل نهاية |

### ما يحتاج جولة تالية (لم يُنفَّذ بعد)
* **حفظ المستندات** ما زال ~٣٠–٣٦ جملة SQL (قيد محاسبي + تسلسل مستندات + تدقيق ×٣ + تحديث الأرصدة).
  الحل: تحويل كتابة القيد إلى `d1.batch()` واحد (الكود موجود في `d1.py`) بدل ٣٦ رحلة.
* تقسيم `pages.js` (209 ك.ب) وتصغيره.
